# Архитектура ServoAI Dashboard — как это работало бы в продакшене

## Общая схема

```
┌─────────────┐    EtherCAT     ┌──────────────┐    WebSocket     ┌─────────────┐
│  Сервопривод │◄──────────────►│  Edge-сервер  │◄───────────────►│  Браузер     │
│  Delta B3-E  │                │  (на объекте) │                 │  Dashboard   │
└─────────────┘                └──────┬───────┘                 └─────────────┘
                                       │ HTTPS/gRPC
                                       ▼
                               ┌──────────────┐
                               │  Облачный     │
                               │  бэкенд       │
                               │  + AI pipeline│
                               └──────────────┘
```

## 1. Сбор данных (Edge)

На объекте стоит промышленный ПК (или Raspberry Pi) с нашим Python-монитором — тем самым `core/telemetry.py`. Он через EtherCAT читает SDO-объекты привода 10 раз в секунду. Но вместо записи только в локальный SQLite, данные параллельно уходят в два потока:

- **Локальная БД** — для работы без интернета, буфер при обрывах связи
- **Очередь сообщений** (MQTT или Kafka) — стрим телеметрии в облако

```python
# Примерно так выглядел бы расширенный _insert:
def _insert(self, sample):
    self._save_to_sqlite(sample)       # локально
    self._publish_to_mqtt(sample)       # в облако
    self._check_local_alerts(sample)    # мгновенные пороги
```

Мгновенные пороги (OV >400В, UV <200В, температура >80°C) проверяются прямо на edge — если DC шина вылетела за 400В, ждать ответа от облака нельзя, нужна реакция за миллисекунды.

## 2. Бэкенд (облако)

Сервер на FastAPI/Django принимает поток телеметрии и раскладывает по трём хранилищам:

- **TimescaleDB** (PostgreSQL с расширением для временных рядов) — вся сырая телеметрия. Запрос типа «покажи скорость за последние 2 часа» — это просто `SELECT ts, velocity FROM samples WHERE device_id = X AND ts > now() - interval '2h'`
- **Redis** — последние значения каждого привода для дашборда реального времени
- **S3/MinIO** — архив для длительного хранения (месяцы, годы)

## 3. AI Pipeline — что происходит «под капотом»

Это самая интересная часть. AI работает не как один волшебный запрос, а как **конвейер из нескольких моделей**, каждая решает свою задачу:

### Слой 1: Детекция аномалий (работает непрерывно, каждую секунду)

Скользящее окно по последним N сэмплам. Для каждого параметра вычисляется — выходит ли текущее значение за статистические рамки, обученные на «нормальных» данных этого конкретного привода.

```
Входит: последние 100 сэмплов velocity, torque, current, temp
Модель: Isolation Forest или Autoencoder (обучен на первых 24ч работы)
Выход:  anomaly_score 0.0 ... 1.0 для каждого сэмпла
```

Например, если привод обычно работает на 1500-1800 RPM, а вдруг скорость упала до 800 RPM при той же команде — autoencoder выдаст высокий anomaly score, потому что комбинация «команда на 1800 RPM + фактическая скорость 800 RPM + возросший ток» не встречалась при обучении.

Это не жёсткие пороги типа «>6000 RPM = плохо». Модель учитывает **корреляции между параметрами**: повышенный ток при высокой скорости — это нормально, а повышенный ток при нулевой скорости — заклинивание.

### Слой 2: Классификация неисправностей (при обнаружении аномалии)

Когда anomaly score превышает порог, запускается классификатор — определяет **тип** проблемы:

```
Входит:  окно данных ±5 секунд от аномалии
Модель:  Gradient Boosting (XGBoost) обученный на размеченных инцидентах
Выход:   {
           "bearing_wear": 0.02,
           "winding_fault": 0.01,
           "mechanical_jam": 0.85,   ← вероятнее всего
           "encoder_error": 0.05,
           "power_issue": 0.07
         }
```

Обучающие данные для этого классификатора — это десятки тысяч записанных инцидентов с разных приводов, где инженеры разметили «вот тут был износ подшипника, вот тут — обрыв фазы». У Delta есть характерные паттерны для каждого типа отказа.

### Слой 3: Прогноз оставшегося ресурса (RUL — Remaining Useful Life)

Раз в час берётся вся история привода и рассчитывается прогноз:

```
Входит:  - Агрегаты за каждый час: RMS тока, средняя/пиковая скорость,
           количество реверсов, набранная температура, счётчик ошибок
         - Возраст привода, общая наработка (часы)
         - Паспортные данные (rated current, rated torque, max speed)
Модель:  LSTM или Transformer, обученный на данных приводов,
         которые уже дошли до отказа
Выход:   {
           "rul_hours": 12400,
           "confidence_interval": [8000, 18000],
           "degradation_rate": 0.003,    # % в час
           "limiting_component": "bearing"
         }
```

Модель буквально видела сотни историй вида «вот так выглядели параметры привода за 3 месяца до отказа подшипника», и ищет похожие паттерны в текущих данных. Если RMS-ток привода последние 2 недели растёт на 0.1% в день при той же нагрузке — это классический признак нарастающего трения в подшипниках.

### Слой 4: Генерация текстового отчёта (LLM)

Вот здесь появляется тот самый AI-текст, который вы видите в блоках на дашборде. Это LLM (Claude API), которому на вход подаётся **структурированная сводка** от слоёв 1-3:

```json
{
  "device": "Delta ASDA-B3-E, серийный #A2341",
  "session_duration_s": 61.1,
  "samples": 605,
  "anomaly_score_avg": 0.03,
  "anomaly_events": [],
  "peak_velocity_rpm": 1789,
  "peak_velocity_pct_of_max": 29.8,
  "rms_current_mA": 47.2,
  "rms_current_pct_of_rated": 1.1,
  "temperature_C": 37,
  "temperature_steady_state_C": 25.04,
  "dc_bus_V_range": [304, 306],
  "error_codes": [],
  "rul_hours": 12400,
  "rul_limiting": "bearing",
  "motion_phases": 3,
  "duty_cycle_pct": 18,
  "classification": { "all_clear": true }
}
```

LLM получает системный промпт вида: «Ты — инженер по предиктивному обслуживанию сервоприводов. На основании данных объясни состояние привода, сравни параметры с паспортными пределами, дай прогноз и рекомендации. Используй конкретные цифры.»

И генерирует те самые блоки текста: «Привод достигал пиковой скорости ±1789 RPM при паспортном пределе 6000 RPM...»

**Важно:** LLM не анализирует сырые данные. Он получает уже обработанные числа от ML-моделей и облекает их в человекочитаемый текст. Это быстро и дёшево — один вызов Claude API на обновление отчёта.

## 4. Фронтенд — что видит пользователь

Сайт на React/Vue, развёрнутый за Nginx на `servoai.example.com`:

- **WebSocket** для live-данных: графики обновляются в реальном времени, KPI мигают при выходе за пороги
- **REST API** для исторических данных: пользователь выбирает диапазон дат, бэкенд отдаёт агрегированные данные
- **SSE (Server-Sent Events)** для алертов: если AI обнаружил аномалию — всплывает уведомление прямо в браузере

Графики с красными/жёлтыми линиями пределов — это то, что у нас уже есть. Разница в том, что данные приходят не из вшитого JS-массива, а из API:

```javascript
// Сейчас (демо):
const data = TELEMETRY;   // 605 вшитых сэмплов

// В продакшене:
const data = await fetch('/api/v1/telemetry?device=A2341&last=1h')
  .then(r => r.json());   // live данные с сервера
```

## 5. Система оповещений

Три уровня:

| Уровень | Условие | Реакция | Время |
|---------|---------|---------|-------|
| **Мгновенный** | OV/UV, перегрев >100°C, error_code ≠ 0 | Edge останавливает привод, SMS/Telegram инженеру | <100 мс |
| **AI-аномалия** | anomaly_score > 0.7 | Push в дашборд, email ответственному | 1-5 сек |
| **AI-прогноз** | RUL < 500 часов, тренд деградации | Создаёт заявку в CMMS (система обслуживания) | 1 час |

## Итого: что делает AI, чего не делает жёсткий порог

Жёсткий порог скажет: «температура 95°C — предупреждение». Но не скажет **почему** она выросла.

AI скажет: «Температура выросла с 37°C до 95°C за последние 3 часа. RMS-ток при этом вырос на 15% при неизменной нагрузке. Это характерный паттерн увеличения трения в подшипниках — совпадает с 87% случаев из обучающей выборки. Рекомендуется замена подшипников в течение 2 недель. Оставшийся ресурс до отказа — ~400 часов.»

Это и есть разница между мониторингом и **предиктивной аналитикой**.
